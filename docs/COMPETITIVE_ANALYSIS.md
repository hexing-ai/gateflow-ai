# 登机口分配 AI 产品竞品分析报告

调研日期：2026 年 10 月 3 日。分析对象：GateFlow 登机口分配 AI 决策工作台。本文基于官方公开资料与公开展示图，服务于产品定位、功能取舍和后续迭代。

市场上已经存在直接竞品，且覆盖了自动分配、多目标优化、情景仿真、实时调整和云端协作。部分厂商还明确使用机器学习、计算机视觉或 AI Agents。GateFlow 选择的切入方向，是帮助计划分析人员更容易理解、比较和复核登机口分配方案。

**产品定位：面向机场计划与运行分析人员的登机口方案评估工作台，通过自然语言配置已支持的目标、调用优化器并解释计算证据，帮助用户判断资源利用与旅客换乘之间的取舍。**这一定位并不意味着市场空白，也不等同于已建立商业竞争优势。

## 调研范围与证据边界

本报告核查了七家国际厂商的相关产品，以及白云信科的国内落地报道；主要依据官方产品页、厂商案例和机场集团资料，共十二项来源。没有登录付费系统、联系销售、进行产品实测或获取报价。

文中“已确认”表示公开资料明确描述该能力，并不代表独立验证了效果。未找到的能力写作“公开资料未确认”，不能推导为竞品没有。商业判断、切入点与建议均属于本报告分析。

比较时区分三个概念：登机口是旅客登机资源，机位是飞机停放资源，靠桥率描述近机位或廊桥使用情况。商业系统往往联合管理它们，但不能把这些对象及其指标直接混为一谈。现有项目中的未分配数也不能直接当作未服务旅客数。

此外，应把机场现有 RMS 的分析模块、自建优化脚本、Excel 与人工协调列为替代方案。这是待用户访谈确认的替代关系，不是对其市场占有率的判断。用户可能已经能完成分配，只是比较方案、解释取舍或协调各方比较费时。

## 最值得深入对标的产品

### Copenhagen Optimization 验证了方案分析的业务价值

Better Stand & Gate 与GateFlow 的离线分析定位最接近。它既面向实时运行，也明确作为分析平台使用，支持目标配置、情景比较、可视化与共享。[7]

厂商的 Minneapolis–Saint Paul 机场案例说明了一个具体任务：机场准备增加一条国际航线，需要评估宽体飞机能否放进已有计划。项目比较了不同航站楼方案对拖曳次数、机位周转间隔和未分配航班的影响，并将结果用于与航空公司沟通。案例称研究在三周内完成，但这是该项目的厂商叙述，不能外推为标准部署时间。[8]

**对我们的启发：**产品价值应从“我用了什么算法”转向“用户完成了什么决策”。GateFlow 提供一个可重复的任务：在相同航班、机位和客流数据下，比较资源利用优先与换乘体验优先的方案，解释受益和受损的旅客组，并导出依据。

**竞争压力：**离线仿真、方案共享和辅助沟通已有供给。必须验证我们能否减少准备与理解方案的时间，不能仅凭轻量界面认定优于竞品。

### Veovo 已经把中转体验纳入资源决策

Veovo 的产品页明确允许机场按自身 KPI 配置计划，包括减少拖曳、改善中转体验和缩短周转时间；同时结合航班、客流与延误预测调整资源，并支持人工控制和数据驱动建议。[6]

**对我们的启发：**“考虑旅客换乘”是有业务依据的方向，但仍需要把指标拆清楚。平均换乘时间、换乘失败人数和换乘紧张程度代表不同问题，应说明计算口径与适用条件。AI 解释必须能回到具体旅客组、航班组合和分配结果。

**竞争压力：**成熟产品能够连通更多资源与实时数据。我们的首版更适合先验证一类清晰的离线决策任务；生产级动态重排需要另外建设数据接入、冲突处理、权限和运行保障。

### Assaia 显示预测与 Agent 正在进入分配环节

Assaia 于 **2026 年 3 月 11 日**公布 StandManager。公告描述了逐航班预测缓冲：当模型判断到达时间变化时，系统在机场规则内重新调整分配。与 ApronAI 联用时，周转表现、拖曳状态及延误预测可以影响机位决策。[4]

同一公告明确提到 AI Agents，但未说明是否提供自然语言对话、采用何种大模型、有哪些工具权限。因此不能把它直接等同于一个聊天式 LLM Agent。公告中的“有效机位容量最多增加 5%”也是供应商主张，缺少足以在本项目复现的公开评测细节，不用于性能排名。

**对我们的启发：**AI 技术的价值取决于它改善了哪一段决策。当前项目更适合先把 AI 放在目标理解、参数配置、工具调用和证据解释上；动态缓冲预测需要额外的真实历史运行数据。

**竞争压力：**“用了 Agent”已不足以作为产品创新结论。更有说服力的是准确处理哪些指令、如何发现不可行请求、如何验证解释，以及用户究竟少花了多少时间。

### Amadeus 与 SITA 给出了基础能力门槛

Amadeus 已提供多 KPI 权重、自动优化与甘特图；SITA 已提供沙盒仿真、一键决策支持和帮助较少经验用户操作的颜色提示。[1][2]

**对我们的启发：**目标配置、占用可视化、冲突提示、候选方案与人工选择，应该当作完成产品闭环的基础能力。AI 辅助需要与这些功能连通，让用户可以检查参数和结果。

这些公开材料未证实两款模块是否已有 LLM 对话界面。应将自然语言工作流视为待测试的设计方向，避免写成“传统系统不会解释，而我们会”。

## 国内竞争与商业信息

国内样本中，白云信科的机位分配报道描述了两套算法的融合，并称系统已在白云机场应用。[11] 这足以说明本土已有围绕规则、多目标与运行场景的落地工作；不能因为公开产品文档较少，就认定国内竞争较弱。

另一个广东省机场管理集团官方页面提到，白云信科的一体化运行管控平台使用数据治理、AI 算法与智能体。[12] **这与机位分配报道是不同项目范围，不能将平台层面的智能体表述直接移植到分配模块。**本轮国内资料覆盖有限，不构成国内厂商排名或完整招投标分析。

价格方面，Copenhagen Optimization 明确表示没有固定价格方案，需按需求报价。[9] 其他所查产品页面主要提供咨询或演示入口，本轮没有获得可比较的报价。AeroCloud 表述不限用户数、不收用户许可证费用，也不意味着整套产品免费。[5]

因此，目前没有依据宣称本项目会“便宜多少”或“部署快多少”。比较总成本还需要纳入数据准备、规则配置、系统集成、培训、维护及后续模型调用成本。

## 哪些差异化值得验证

| 候选方向 | 竞争证据带来的限制 | 建议的验证方式 |
| --- | --- | --- |
| 自然语言完成目标配置与方案追问 | 本轮未确认各产品的具体对话能力；Assaia 已提 Agent | 让相同用户用表单与对话完成相同任务，比较成功率、纠错次数、用时和成本 |
| 展示可复核的换乘取舍 | Veovo 已强调中转体验；多目标也已有供给 | 检验用户能否正确说明为何选 A、放弃 B，以及哪些旅客组受到影响 |
| 小数据集即可完成离线分析 | Copenhagen Optimization 已有快速配置的分析案例 | 记录从获得合格数据到首次有效比较的实际时间，区分数据清洗与求解时间 |
| 开放可复现的演示与评测 | 透明度不等于商业壁垒，竞品也可能有相关机制 | 发布可授权的数据样例、配置、结果和评测方法，让第三方复现核心结论 |
| 中文业务表达和术语解释 | 未调查各厂商本地化版本，不能宣称其不支持中文 | 使用真实岗位语言测试参数映射和解释准确性，积累经验证的业务案例 |

建议优先组合前两项，第三项作为采用门槛，第四项用于公开仓库的可复现性。真正可能逐步形成积累的是机场规则、被验证的决策案例、可靠的数据适配和用户反馈，而不是单一聊天界面或模型名称。

## 根据竞品结果安排迭代

GateFlow 以“单一机场历史运行日的方案评估”为核心任务。流程为：导入数据 → 明确运行日和数据问题 → 配置目标 → 生成候选方案 → 检查冲突并比较指标 → 解释取舍 → 人工选择并导出。

| 优先级 | 能力方向（当前实现见上表） | 对应的决策价值 |
| --- | --- | --- |
| P0 | 数据解析、统一指标、固定随机种子、独立约束检查 | 确保比较可信，是后续所有功能的前提 |
| P0 | 上传与检查、运行进度、甘特图、方案指标及差异表 | 让用户能够完整完成一次方案选择 |
| P0 | 导出数据版本、参数、分配结果、检查结论和解释依据 | 使方案可复核、可讨论、可重现 |
| P1 | 自然语言配置已支持的目标，调用求解器，基于结果回答追问 | 验证 AI 是否降低操作和理解成本 |
| P1 | 缺字段、不可行方案、求解失败和未知约束的处理 | 检验真实工作流是否可靠 |
| 后续 | 航班锁定、机位关闭、延误重排等场景 | 先补模型与校验，再对用户开放自然语言操作 |
| 后续 | 动态预测缓冲、实时接口、多方协作、企业部署 | 依据实际试点数据和使用需求安排 |

产品形态采用 **Web 决策工作台＋受约束的 AI 辅助＋优化器**。AI 辅助负责理解与编排，优化器负责计算，独立校验负责检查硬约束，用户负责选择和确认。现阶段没有证据表明多 Agent、长期记忆或某种特定模型能带来必要增益，应围绕任务评测选用。

## 用什么验证市场与 AI 价值

优先访谈机场计划编排、运行分析或相关咨询人员，采购者和系统运维人员在后续补充。以下是建议的初步研究安排，不是已经完成的访谈：先做约五至八位相关人员的探索访谈；若暂时只能接触教师或研究人员，应将结果定位为教学与仿真需求验证。

访谈应围绕近期真实任务展开：最近一次难以决定的分配发生了什么；现有系统能输出什么；哪一部分仍需在表格中处理；方案需要向谁解释；什么情况下会拒绝采用建议；谁能提供脱敏数据、谁决定试用和采购。

| 验证问题 | 测量方式 | 如何用于产品决策 |
| --- | --- | --- |
| 计算是否可信 | 独立复算已建模的硬约束，记录输入版本、可行率和指标口径 | 有违反硬约束的方案必须明确标识，不能包装成可采用方案 |
| AI 是否帮助完成任务 | 同一批任务比较表单版与 AI 版，记录成功率、操作时间、错误及调用成本 | 若收益有限，缩小对话职责，保留有价值的解释能力 |
| 用户是否理解取舍 | 让用户复述选择原因及受影响对象，核对是否与计算结果一致 | 优化指标呈现与证据入口，而非只提高回答流畅度 |
| 解释是否忠实 | 检查所有数字、引用规则和因果表述是否能对应到计算或已给条件 | 将无依据数字、虚构约束和夸大收益设为阻断问题 |
| 是否存在采用需求 | 是否愿意提供合规样本、反复完成任务、参与后续试点 | 感兴趣与愿意付费分别记录，不将演示好评当作商业验证 |
| 算法内部 LLM 是否有增益 | 纯 NSGA-II、固定启发式、随机参数和 LLM 参数方案做公平预算、多种子对照 | 独立决定是否保留；用户侧 Agent 不依赖它成立 |

建议的商业验证顺序是：可复现公开演示 → 与有真实问题的团队开展离线评估试点 → 根据重复使用与付费意愿决定软件订阅、分析服务或两者结合。此路径降低了首期对生产系统集成的依赖，但并不消除数据准备和获取用户的难度。
